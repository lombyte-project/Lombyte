# Matching tips

[CONTRIBUTING.md](../../CONTRIBUTING.md) has the step-by-step loop and the
commands. This page is the "why" behind it. Read it before you promote a unit.

## The basics

- The retail executable (`SCUS_971.99`) is the only truth. Every claim points
  at an address, a byte range or a hash.
- Two separate goals: the rebuilt image matches byte for byte (always true),
  and the code is readable C (the work in progress). Keep them apart.
- Every byte range has one owner. A unit that is not in C yet is built from
  assembly made from your own executable at build time (`INCLUDE_ASM`, in
  `config/us/expected/asm/`, not in Git), so the image always matches.
- A unit becomes C only when its whole range matches. The assembly goes away
  only after every check passes.

## Which compiler

- Retail used two compilers: the SDK compiler for the SDK libraries and the
  game compiler for everything from `GAME_TEXT_START` on. A unit's compiler
  follows from where retail put it, not from which compiler happens to match.
  Folder names and single examples are not evidence.
- A per-unit compiler flag is a last resort, and we are removing the ones we
  have. Add one only when you measured the difference, the source or a
  fixable compiler bug does not explain it, and the reason sits next to the
  flag in `configure.py`.
- `ROUTE_EXCEPTIONS` (top of `configure.py`) lists units that do not match on
  their own compiler yet, and what still builds them. It only gets shorter.

## The loop

1. Read the whole function, its callers and callees. Recover types, struct
   layouts, signatures, and one or two matching neighbours.
2. Write readable C for it.
3. Compile and compare (`check-unit.py`).
4. Name the first difference: control flow, calling convention, field size or
   sign, addressing, variable lifetime, order, scheduling.
5. Change one thing, compile again. Keep it only if it is strictly better;
   otherwise go back to the best version.
6. If the same kind of difference survives three tries, change approach: find
   missing context, try another source shape, or move down the list below.

Try several variants of one idea (mirrored branches, hoisting, widths,
temporaries) together rather than one by one. Look at the full aligned
instruction listing before changing order or addressing; filtered diff rows
are not aligned pairs.

## When you are stuck

Go down this list in order:

1. More context: field sizes, pointer chains, calling convention, layouts,
   neighbours.
2. Source shape: evaluation order, temporaries, branch direction, loop form,
   declaration size.
3. Compiler flag tests tied to a clear idea about the generated code.
4. Automated search (permuter) for register choice, store order or delay
   slots.
5. A compiler fix, when the needed code cannot come out of the compiler.
6. Park it: write down what you tried, the first difference and what would
   make it worth another look (in the pull request or an issue).

A failed search does not prove it is impossible, and a higher score never
justifies changing what the code does.

## What "exact" means

- 100 % code, functions and data for the unit, and the whole rebuilt image
  matches byte for byte.
- A high objdiff score is not exact: objdiff ignores relocations. The bytes
  must match at the retail address, and then `make elf` must pass.
- Run `make elf` once per batch of promotions. If it fails, bisect the batch.

## Promoting a unit

- Put it in the folder of its subsystem. Units still in assembly stay under
  `assembly/<subsystem>/`.
- Keep the linker symbol (`FUN_<address>`) as an `__asm__` label on the
  declaration and give the C function a real name only when the evidence
  supports it ([code-cleanup.md](code-cleanup.md#names)).
- Progress numbers come from the tree; never edit them by hand.

## Small things worth knowing

- Segment boundaries and the undefined-function list are kept by hand. Tools
  that guess them are a starting point only; a wrong entry fails `make elf`.
- Small-data variables belong to the file that defines them. Ps2EeAs uses
  `$gp`-relative access only when it already knows the variable's size: in a
  delay slot (`.set nomacro`) or after the definition in the same file. So a
  unit that retail reaches through `$gp` outside delay slots defines the
  variable itself, before its functions, and is listed in `SDATA_OVERLAYS`.
  Functions that share such a variable live in one file
  (`rendering/vu1/vu1_chain.c`, `audio/rpc/snd_returns.c`). No
  `__asm__(".extern ...")` is needed.
- Do not change code for style when it changes the generated bytes.
- Never commit game data, disc images or compiler binaries.
- Tests for the build scripts are in `scripts/test_public_tools.py`.
